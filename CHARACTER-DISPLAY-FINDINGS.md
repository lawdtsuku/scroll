# Character display pass — read-only findings, 2026-10-04

Baseline: 0.5.2, fbfc4aecc8ea3f4abd2a66735337981af41aad49.

1. `dist/style.css` clamps `.ability-cost` and `.ability-effect` with `-webkit-line-clamp` and `overflow:hidden`. Both are children of a native `<summary>` in `abilityList` in `dist/app.js`. The baseline browser test opened the ability by clicking its name. The reported iPhone text-tap failure was not reproduced; a device/build-specific cause remains unconfirmed. Expanded previews currently remain in the summary and duplicate the full definition list.
2. `progressHTML` prints `i+1`, while `thresholdList` prints `g.stage_index`. `validateScheduler` requires `g.stage_index === i` for array entries: stored stages are zero-based. Display numbering can consistently be one-based without changing stored values.
3. `set_threshold_dc` in `dist/progress.js` checks the character, threshold, stage, integer DC and allowed fields. It does not prohibit a completed threshold. Keep this valid protected action under Manage for completed thresholds. `log_threshold_attempt` separately rejects completed thresholds and non-current stages.
4. `memberCard` in `dist/roster-view.js` is shared between operator and snapshot viewer. Ability rendering and owner attributes/resources were duplicated in `app.js` and `snapshot-app.js`. Snapshots do not carry character XP boundaries or training thresholds; matching those unavailable values would require an out-of-scope export change. Shared rendering must show next threshold not set when no boundary was provided.
5. `sw.js` caches a fixed asset list on install and serves cache-first for same-origin GET requests. It deletes older Scroll caches on activation. There is no skipWaiting or clients.claim. `app.js` registers the worker and checks `registration.waiting` at registration and installation state changes, displaying a five-second toast: “Update ready. Save edits, then close all Scroll windows and reopen.” A waiting worker normally activates after all old controlled clients close. An offline device, a still-open old client, or a device that never completes an update check can remain stale indefinitely. A missing field on an old immutable receipt alone is not proof of a stale running build. Proposal only: a persistent update-ready panel and explicit safe activation flow could improve this later. This pass adds the visible version/build label and caches its new modules; worker lifecycle is unchanged.
6. `visibleEvents` filters `state === 'triggered'`; the standing chain predicate filters `selection_rule === 'trigger_chain' && state === 'scheduled'`. Neither reads dates. The saved pending-remainder flag already drives Play's travel notice. They can share a UI attention helper without consulting future timing. The XP notice is separate and does not feed the Play badge.
7. The existing checklist can already reach All done with attention present if state was copied, but a standing chain notice still shows as attention. A device-only acknowledged-ID set removes that standing notice from UI attention, not from exports. New IDs relight; decreases do not; an empty set clears the saved acknowledgment.

Scope decisions: no app_version export field; no schema, IndexedDB version, operation or token changes. Preserve exact free text. No extrapolated XP boundary or invented snapshot training data. Prior 0.5.1 render-parity claims intentionally no longer apply to these redesigned screens; data/export parity remains tested.
